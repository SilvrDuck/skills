# Claude Code implementation notes

Use this reference only when the harness is Claude Code. Inspect the installed version, effective plan, model catalog, and real executable rather than trusting aliases or hard-coded generations.

## Fixed-plan requirement

Unattended operation must remain inside the user's fixed Claude subscription allowance.

- Verify subscription authentication before starting.
- Reject `ANTHROPIC_API_KEY`, cloud-provider API credentials, pay-as-you-go routing, extra usage, and any fallback that can create a separate bill.
- If billing mode cannot be established, stop.
- A model alias is acceptable only when it is verified to use the same fixed plan.

## Session scheduling is not durable

Claude Code session cron and wake tools are temporary coordination features, not unattended infrastructure:

- they disappear with the Claude session or depend on it remaining alive;
- recurring jobs expire;
- wake delays may not span the daytime gap;
- any `durable` label does not make them host-persistent.

Use them only for an explicitly temporary interactive run. For unattended operation, install a host scheduler and set `scheduler.self_schedule` to `false`.

## Durable host scheduling

Detect the host rather than copying one Linux recipe everywhere:

1. **macOS:** generate a user LaunchAgent plist under `~/Library/LaunchAgents/`, using `StartCalendarInterval` entries for configured working hours. Load it with `launchctl bootstrap gui/$(id -u) ...` and verify with `launchctl print`.
2. **Linux with systemd user services:** generate a user service and timer under `~/.config/systemd/user/`. Use the configured timezone when supported, enable lingering only after explaining and obtaining consent, and verify with `systemctl --user status` and `list-timers`.
3. **Cron fallback:** install a user crontab entry. Use `CRON_TZ=<configured timezone>` only after verifying that the host cron supports it; otherwise generate timezone-correct entries or prefer launchd/systemd. Enumerate only working-hour fires where practical and use a stable off-`:00` minute.

The scheduler invokes `.agent-platform/heartbeat.sh`; it is the sole clock. Keep an exact copy of installed configuration under `.agent-platform/host/` and store its identifiers in state so `stop` removes only platform-owned entries.

## Canonical wrapper shape

Generate paths from the current host. Do not hard-code this example:

```bash
#!/usr/bin/env bash
set -uo pipefail

export HOME="<resolved-home>"
export PATH="<minimal-explicit-path-containing-project-toolchain>"
ROOT="<resolved-repository-root>"
CLAUDE="<resolved-real-claude-binary>"
RAW_LOG="$ROOT/.agent-platform/runtime.log"
LOCK="$ROOT/.agent-platform/heartbeat.lock"

cd "$ROOT" || {
  printf '%s FATAL: cannot enter repository\n' "$(date -Is)" >>"$RAW_LOG"
  exit 1
}

# Use flock when available; otherwise use an atomic lock directory with cleanup.
# Enforce a watchdog shorter than the heartbeat interval using timeout, gtimeout,
# or a small portable watchdog generated by the platform.

"$CLAUDE" -p \
  "Invoke agent-platform and execute exactly one heartbeat. Read HEART.md and .agent-platform/state.json first." \
  --permission-mode acceptEdits \
  --allowedTools Bash Read Write Edit Glob Grep WebFetch WebSearch TodoWrite Task \
  --model "<verified-general-fixed-plan-model>" \
  --effort medium \
  >>"$RAW_LOG" 2>&1
```

Everything is deliberate:

- scheduler jobs lack shell aliases, functions, and login startup files;
- set `HOME` and a sufficient explicit `PATH`;
- resolve the real binary with `type -a claude`, `command -v claude`, and `readlink -f` where available;
- never invoke an interactive wrapper that injects higher effort;
- use a non-blocking lock to skip overlap;
- use a timeout shorter than the interval;
- keep raw stdout/stderr separate from curated `LOG.md`.

On macOS, account for the absence of GNU `timeout` and often `flock`; use installed `gtimeout` only when already available, otherwise generate portable watchdog and lock-directory logic. Do not install global packages without consent.

## Headless permissions

Do not edit `.claude/settings.json` merely to make unattended execution work; the permission classifier may block that edit and repository settings are not the right place for host bootstrap.

Use command-line scoping:

```text
--permission-mode acceptEdits
--allowedTools Bash Read Write Edit Glob Grep WebFetch WebSearch TodoWrite Task
```

This is configured autonomy, not blanket bypass. Do not use `--dangerously-skip-permissions`.

The allowlist is not an OS-level filesystem jail: Claude runs as the host user. Keep repository restrictions explicit in HEART and the wrapper prompt. Offer optional hardening through a systemd sandbox, bubblewrap/firejail on Linux, or an appropriate macOS sandbox/container, but do not claim the harness allowlist alone is a hard jail.

## Bare-environment verification

Before reporting success, test the real binary under a scheduler-like environment:

```bash
env -i \
  HOME="<resolved-home>" \
  PATH="<minimal-explicit-path>" \
  "<watchdog-command>" \
  "<resolved-claude-binary>" -p "Reply with exactly the word: READY" \
  --model "<verified-fast-fixed-plan-model>" \
  --effort low
```

Require output `READY` and exit code `0`. Confirm authentication came from the fixed subscription. Do not solve a failure by exporting an API key.

Then execute the generated wrapper detached from the interactive session, verify start/end markers and exit status in `runtime.log`, test that a second concurrent invocation skips, and confirm the host scheduler is installed and active.

## Models and token economy

Inspect the effective fixed-plan model catalog. Capability classes are stable; concrete IDs are examples and may change:

| Class | Candidate | Use |
|---|---|---|
| fast | verified Haiku-class model | polling, extraction, marking, mechanical checks, log synthesis |
| general | verified Sonnet-class model | heartbeat lead, normal coding, investigation |
| strong | verified Fable/Opus-class model when included | one rare deep synthesis, hard diagnosis, adversarial review |

Pin the unattended lead model and `--effort medium` explicitly. Never let an interactive function such as `claude --effort xhigh` leak into the scheduler. Use low effort for cheap checks and escalate only for a justified deep step.

Do not assume a strong model is included. On rejection, fall back once, update state, and stop trying. If allowance information is exposed, record it and reduce scope, effort, and fan-out as the reset approaches. Never enable extra usage.

## Orchestration

- **Subagents:** default for focused independent work.
- **Agent teams:** only when peers need shared tasks or direct communication.
- **Dynamic workflows:** repeatable high-fan-out work, with cheap stages routed to fast models.

The user may choose a numeric concurrency cap or `token-managed, no fixed cap`. The latter is not permission to maximize fan-out: the lead must allocate the fixed allowance parsimoniously. The lead remains responsible for HEART interpretation, final synthesis, state, logging, and scheduler ownership.
